# 知识条目：资料库由对话积累而成

日期：2026-08-22

## 问题

资料库现在装的全是预设内容。`content/nutrition`、`content/preparation` 是随 App
发布的静态 YAML，用户加不进任何东西；三个"可写"的分类写进去的只是问题文本和
勾选状态，不是有价值的资料。

用户要的是：跟 AIM 聊到一道适合孕期的菜，就能把菜谱（食材、做法）存进资料库；
问到某样东西能不能吃，就能把结论和原因存下来。资料库应当是**聊出来的**，
不是发布时就定死的。

## 模型

新增 `RecordType.knowledge`。一条知识条目 = 归属分类 + 形态 + 该形态的结构化内容。

**为什么是记录而不是新表**：直接复用增删查、家庭可见性、软删除，以及
`list_records` 已有的读取路径。

**四种形态**，各自有结构（已确认「每种形态各自结构化」）：

| 形态 | 字段 | 典型内容 |
| --- | --- | --- |
| `recipe` | `ingredients[]`、`steps[]`、`note?` | 菜谱：食材与做法 |
| `food_rule` | `verdict`、`reason`、`note?` | 能不能吃：结论 + 为什么 |
| `howto` | `steps[]`、`note?` | 办证、操作类的步骤 |
| `tip` | `body` | 一段说明，兜底形态 |

`verdict` 取值 `safe` / `limit` / `avoid`。三档而不是"能/不能"二档，因为孕期饮食
大量情况是"可以但要限量"，二选一会逼出错误的绝对化结论。

结构化的代价是每加一种形态要改 schema 与工具；换来的是菜谱能渲染成食材清单
加编号步骤，而不是一坨字。

## 与 Agent 的关系

新增 `create_knowledge` 工具，**走「执行前确认」档**（已确认）：模型先给出预览，
用户确认后才写入。与建待办、记记录的"直接执行"不同——知识条目内容长，
且经常是模型总结出来的，先看一眼再存。

客户端需要一种新的预览卡形态：现有的 `AgentChangePreview` 只覆盖对已有任务的
字段级 diff，无法表达"一条待新增的菜谱长什么样"。

## 静态内容

`content/nutrition` 与 `content/preparation` 删除，改由用户积累（已确认）。

`content/safety-rules` **暂时保留只读**。它是"出现这些情况立即就医"的急救提示，
恰恰是用户最不可能自己先录进去的内容；改成用户条目意味着新用户进来时没有任何
安全兜底。此项待产品确认后再处理。

`content/hangzhou` 保留：它是政策核对入口，按 ADR 的既有原则不能由用户或模型
断言政策结论。

## 分类与形态的关系

分类（吃什么、办事指南……）决定条目出现在哪张卡下；形态决定它怎么渲染。
两者独立——办事指南下既可能有 `howto`，也可能有 `tip`。

`checklist` 记录保留：勾选状态和知识条目是两回事，待产准备既有"要带什么"的
知识条目，也有"带了没有"的勾选。

## 测试

- 领域：四种形态各自的校验；未知形态、未知分类、`verdict` 非法值都要挡住；
  `recipe` 没有食材或没有步骤要挡住。
- 工具网关：`create-knowledge` 写入后能被 `list_records` 读到，且带上 agent 来源。
- Eve：`create_knowledge` 保留 approval，与 `create_task` 的直接执行档形成对照。
- 客户端：预览卡按形态渲染；确认后条目出现在对应分类下。

## 不做什么

- 不做条目的编辑界面（第一版由 Agent 写、用户删；改用重新生成一条替代）。
- 不做全文搜索。
- 不改 `undo_operation` 的既有语义。
