# 密码账号体系

替换掉演示登录：注册、登录、会话、密码重置。不使用短信验证。

## 为什么现在做

`POST /api/v1/auth/demo-session` 是当前**唯一**的登录方式：给任意手机号即建即用，
无任何凭证。服务器部署在公网 IP 上，这意味着任何人扫到 80 端口都能创建账号、
读写家庭数据。

## 决定

| 项 | 选择 | 理由 |
|---|---|---|
| 账号标识 | 手机号 | 沿用现有 `accounts.phone` 唯一约束，家庭邀请机制不用动 |
| 注册时的角色 | 三档可选，不再写死 mother | 见「家庭角色与称呼」 |
| 孕期归属 | 属于家庭，不绑定成员 | 现有模型已如此，爸爸可以先注册 |
| 注册策略 | 开放注册 | 见下方「已知取舍」 |
| 密码找回 | 服务器命令行重置 | 无短信无邮箱，自助找回在技术上不成立 |
| 会话时长 | 30 天 | 见「会话」一节 |

## 账号与密码

`accounts` 增加 `password_hash TEXT NOT NULL`（Alembic 迁移）。库当前为空，
无存量账号需要迁移。

**密码规则只要求至少 8 位**，不设大小写/数字/符号的组合要求。组合规则逼出来的是
`Passw0rd!` 这类可预测密码，长度才是真正起作用的维度（NIST SP 800-63B 同此结论）。

哈希用 **argon2id**（`argon2-cffi`，已随现有依赖安装，需在 `pyproject.toml` 显式声明）。
不用 bcrypt：它在 72 字节处静默截断，超长密码会被无声削弱。

## 接口

| 接口 | 行为 |
|---|---|
| `POST /api/v1/auth/register` | 手机号 + 密码 → 建账号、建家庭、返回 token |
| `POST /api/v1/auth/login` | 手机号 + 密码 → 返回 token |
| ~~`POST /api/v1/auth/demo-session`~~ | **删除**，连同 `DEV_AUTH_ENABLED` 设置项 |

删除演示入口不是可选项。开放注册的前提下若保留免密通道，任何人仍可绕过密码进入，
密码就只是装饰。

**登录失败一律返回同一条消息**（「手机号或密码不对」），不区分「账号不存在」与
「密码错误」。区分了，这个接口就成了手机号枚举器——攻击者能用它探明哪些号已注册。

**nginx 限流必须一起改。** 现有配置是精确匹配：

```nginx
location = /api/v1/auth/demo-session {
    limit_req zone=aim_login burst=3 nodelay;   # 5r/m
}
```

删掉 demo-session 后这个 location 就没有任何请求会命中，注册和登录会落到
`location /api/` 的 20r/s 那一档——等于对着密码接口敞开暴力破解。改成前缀匹配：

```nginx
location /api/v1/auth/ {
    limit_req zone=aim_login burst=3 nodelay;
}
```

5 次/分钟对真人登录绰绰有余，对猜密码则是有效的减速带。

## 会话

当前 token 有效期是 **1 小时**（`platform/auth/context.py`，`issued_at + 3600`）。
免密时代这没有代价，重登一次即可；加了密码之后它变成「每小时手输一次密码」。

改为 **30 天**。孕期 App 是每天要用的工具，不是网银。

**不做 refresh token。** 它需要额外的令牌存储、轮换和撤销逻辑，而当前没有对应的
威胁模型能证明这份复杂度值得。等真有「远程登出」这类需求时再引入。

## iOS

登录页拆成「登录 / 注册」两段，密码用 `SecureField`。token 继续存 Keychain。

401 自愈路径已经就位（`aimSessionExpired` 通知 → `AppSessionStore.clear()` → 回登录页），
密码错误与会话过期都会干净地退回登录页，不需要额外处理。

## 家庭角色与称呼

注册时 `role` 被写死成 `mother`（`identity/.../router.py`），家庭名被写死成
「我的家庭」。用户没有任何机会说明自己是谁，选错也没有补救路径。

**注册表单增加角色选择和称呼。** 角色沿用后端已有的三档：

| 值 | 显示 |
|---|---|
| `mother` | 妈妈 |
| `father` | 爸爸 |
| `other_caregiver` | 其他家人 |

**孕期属于家庭，不绑定到具体成员。** 现有数据模型（`pregnancies.family_id`）已经是
这样，不需要改表。这意味着爸爸可以先注册、先建家庭、先填预产期——填的是「家里的
预产期」而不是「我的预产期」。

**`family_members` 增加 `nickname VARCHAR(60) NULL`。** 成员目前只有角色没有名字，
两个「其他家人」在列表里完全一样，分不出谁是谁。称呼在注册时填（如「婆婆」「小李」），
为空时回退显示角色名。

新增两个接口：

| 接口 | 行为 |
|---|---|
| `PATCH /api/v1/families/{family_id}` | 改家庭名 |
| `PATCH /api/v1/families/{family_id}/members/me` | 改自己的称呼和角色 |

只能改自己的成员信息——改别人的需要一套权限模型，而当前没有需求支撑它。

**本次不做**（用户明确未选）：移除成员、退出家庭、成员详情页。

## 密码重置

`services/api/scripts/reset_password.py`，在服务器上手动执行。

不做密保问题：密保答案通常比密码更好猜（「你母亲的姓氏」），等于给账号开一道
更弱的后门。

## 测试

后端：注册成功、重复手机号、密码过短、登录成功、密码错误、账号不存在（与密码错误
返回一致，防枚举）、token 过期时长、三种角色都能注册、称呼可空时回退到角色名、
只能改自己的成员信息。

iOS：14 个现有 UI 用例目前全部依赖 `demo-session`，删除后必须改为走真实注册流程。
这部分工作量不小，但不改就失去全部端到端验证。

## 已知取舍

**开放注册 + 明文 HTTP。** 服务器无 TLS，密码将以明文经网络传输，同一 WiFi 下抓包
即可获取。开放注册意味着任何人可创建账号。

这两点都是在明确知情下作出的选择（2026-08-25），不是疏漏。密码在此环境下提供的
保护有限——它挡住的是随手扫端口的人，挡不住在链路上的人。

接入真实用户前的前置条件：配置域名 + HTTPS，并删除 `Info.plist` 中的
`NSAppTransportSecurity` 段。
