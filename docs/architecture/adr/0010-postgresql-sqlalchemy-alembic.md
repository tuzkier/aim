# ADR-0010：使用 PostgreSQL、SQLAlchemy 2.0 与 Alembic

## 状态

已接受

## 背景

产品的家庭成员、孕期档案、阶段计划、待办、健康记录、Agent 运行和 Tool 执行之间存在明确关系，并且需要事务一致性、可追溯修改和结构化查询。服务端已确定使用 Python 与 FastAPI，数据访问层需要兼顾类型表达、迁移可靠性和单人长期维护成本。

结构化业务事实已经被确定为系统真相，Agent 推断和对话内容不能替代正式业务记录。因此，主数据库应优先保证关系约束和事务能力，而不是以灵活文档结构为核心。

## 决策

使用以下持久化技术组合：

- PostgreSQL 作为结构化业务数据的主数据库；
- SQLAlchemy 2.0 作为 ORM 与数据访问基础；
- Alembic 管理数据库结构迁移；
- Pydantic 模型用于 API 输入输出和边界校验，不与 ORM 模型共用同一套类；
- 核心事实使用明确的关系表、约束和字段表达；JSONB 仅用于 Agent 运行快照、供应商原始响应、可变元数据等不适合作为核心查询真相的内容。

业务用例通过明确的数据访问接口操作持久化数据，不允许 FastAPI 路由或 Agent Tool 任意跨层直接写表。数据库驱动、同步或异步 Session 策略将在运行模型确定后单独决策。

## 影响

### 正面

- 适合家庭、孕期、计划、任务和记录之间的关系与事务；
- 数据约束可以阻止 Agent 或接口写入不完整、相互冲突的核心事实；
- SQLAlchemy 与 Alembic 的职责清晰，便于 Coding Agent 生成、审查和测试迁移；
- API 契约与数据库模型分离，避免外部接口变化直接污染持久化结构。

### 负面

- API Schema、领域对象和 ORM Model 之间需要显式转换；
- Alembic 自动生成的迁移仍需人工或 Coding Agent 审查，不能无条件直接执行；
- 复杂查询和事务边界需要形成统一编码规范。

### 中性

- Redis、对象存储和搜索能力如后续采用，只承担特定职责，不取代 PostgreSQL 的主数据地位。

## 备选方案

- SQLModel：模型声明更紧凑，但容易把 API、校验和持久化模型耦合在一起，不利于长期边界维护；
- Django ORM：能力成熟，但服务端 Web 底座已确定为 FastAPI，引入 Django 仅作为 ORM 会增加框架重叠；
- MongoDB：适合灵活文档，但本产品核心数据关系明确、事务和事实约束优先；
- 直接编写 SQL：控制力高，但会增加常规数据访问和迁移的维护成本，可在确有必要的复杂查询中局部使用。
